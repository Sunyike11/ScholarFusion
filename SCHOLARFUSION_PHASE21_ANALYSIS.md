# ScholarFusion Phase 2.1 Analysis

Phase name: Production Path Validation, Model-Reviewed Evaluation and Ablation.

## Current Retrieval Path

`ResearchService.search_text`, `search_figures`, `search_any_to_any` and `qa` call `HybridResearchRetriever`.

`HybridResearchRetriever` combines:

- optional `LegacyProductionRetrieverAdapter`
- `ScholarFusionRetriever`
- optional graph retrieval
- `WeightedRRF`

`ScholarFusionRetriever` invokes:

- `bm25`: current structured-element lexical retriever in `ResearchRetriever`
- `text_dense`: SQLite vector collection `research_text_elements`
- `multimodal_dense`: SQLite vector collection `research_multimodal_elements`
- `page_visual`: SQLite vector collection `research_page_visual`
- `paper_level`: SQLite vector collection `research_paper_level`

## Legacy Chroma / BM25 Status

The original LlamaIndex Chroma/BM25/reranker path remains in the legacy RAG application, but Phase2 ScholarFusion smoke did not instantiate that workflow. The adapter can consume an initialized workflow, but current ResearchService default does not automatically attach it. Therefore:

- BM25 in current ScholarFusion smoke is not the original LlamaIndex BM25.
- Text Dense in current ScholarFusion smoke is not the original Chroma collection.
- The current production validation must mark SQLite dense + structured lexical as the validated path and legacy Chroma/BM25 as adapter-ready but not fully proven in this phase.

## Multimodal / Page / Paper / Graph Indexes

- Multimodal Dense: `ScholarFusionVectorIndex`, collection `research_multimodal_elements`.
- Page Visual: rendered PDF page images embedded into `research_page_visual`.
- Paper-level: paper title, abstract and card summary vectors in `research_paper_level`.
- Graph: SQLite graph tables managed by `ScholarFusionGraphStore`.

## Reranker

Default service uses deterministic fallback to avoid paid API calls during tests. Real reranker is enabled by:

```text
SCHOLARFUSION_ENABLE_REAL_RERANKER=true
```

Provider:

```text
qwen3-vl-rerank
```

Phase2 real smoke succeeded on a small text candidate set.

## Current Evaluation Runner

`scripts/run_scholarfusion_lite_evaluation.py` runs a single fixed retrieval/QA path. It does not yet support B0-M5 component switches. It reports legacy citation metrics plus primary/context split metrics.

## Candidate / Evidence Generation

`scripts/build_scholarfusion_lite_eval.py` creates provisional candidates from structured elements, figure captions and linked IDs. Evidence IDs are generated from the element used to create the question and nearby figure links. They are not human reviewed and may be incomplete.

## Why Claim Support Is High But Citation Precision Is Low

Claim support is computed against the evidence bundle actually used by QA, using deterministic token overlap. Citation precision is computed against candidate `relevant_element_ids`, which are sparse auto labels. A cited paragraph can be valid evidence but absent from the candidate label list. This explains high claim support and very low primary citation precision.

## Answerable Labels

Answerable labels are generated by candidate type:

- element/figure-derived items are answerable
- private deployment latency questions are unanswerable

These labels are provisional and need independent review.

## Review Queue Status

`evaluation_data/scholarfusion_lite_v1/phase2_review_queue.csv` has 30 rows but only compact evidence IDs. Phase2.1 needs evidence previews, model review output, rejected rows and spot-check CSV.
